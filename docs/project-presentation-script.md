# Inventory Management System — Presentation Script

A spoken walkthrough of the Inventory Management System project: a raw-PHP and MySQL backend that talks JSON over HTTP, and a React frontend that consumes those endpoints end-to-end. Three versions — pick whichever fits the time you have.

---

## Version A — One-minute pitch (~140 spoken words)

I built an Inventory Management System for small shops — products, suppliers, categories, and the stock that moves in and out. On the backend I used raw PHP and MySQL, one small PHP file per endpoint, all returning JSON. Login sets a session and the browser holds onto an HttpOnly cookie, so there's no token to manage. Stock-in and stock-out records are immutable — history can't be quietly rewritten. The frontend is React with Vite, and it talks to that PHP API in a clean three-layer separation: Axios handles the wire, TanStack Query handles the cache, and the pages only ever render. Forms mirror the backend's validation rules, so feedback is instant in the browser, but the server still has the final say. End result: a working, honest inventory app a CSE student can demonstrate without standing on ceremony.

## Version B — Five-minute walkthrough (~720 spoken words)

The project is an Inventory Management System for a small retail or stockroom — products, categories, suppliers, and a record of every stock-in and stock-out movement. It's split into two halves: a raw-PHP and MySQL backend that exposes a JSON API, and a React frontend that consumes it.

On the backend, I deliberately avoided a framework. Every endpoint is a single PHP file — one for login, one for listing products, one for recording a stock-out, and so on. They all read from the same MySQL database and they all return JSON in the same envelope: success flag, a data field, a human message, and an optional errors object keyed by field. That consistent shape is what lets the frontend react predictably. Authentication is session-based: when you log in, the server sets an HttpOnly cookie in your browser. Every subsequent request carries that cookie automatically, and the server either accepts it or responds with a 401. There's no token to store and no token to steal through JavaScript.

The data model is intentionally tight. Products belong to one category and one supplier. Stock-in and stock-out are separate tables that both point at a product — and once a record lands in those tables, it cannot be edited or deleted. The business rule is that if you make a mistake, you record a compensating entry, the same way an accountant doesn't erase a journal entry. On top of that, deleting a product that has stock history is rejected by the backend with a 409 conflict, and deleting a category or supplier doesn't fail — instead, referencing rows become null, because that's what the foreign keys are configured to do.

The frontend is a React app built with Vite. When it boots, before any other request, it calls an endpoint that asks the server "who am I" — if the answer is a user, the app shows the dashboard; if it's a 401, the app redirects to login. That single check is what makes refresh work without writing any token storage logic. Throughout the app, three kinds of state are deliberately kept separate. Data that lives on the server — product lists, stock history, dashboard totals — goes through TanStack Query, which caches and refetches it. A few app-wide things, like the current user and the light-or-dark theme, sit in React contexts. Everything else — which modal is open, what filter is on the page — stays local to the page. Filter and pagination state actually lives in the URL, so I can copy a link to "products above minimum stock, page 2" and someone else can open it and see exactly what I saw.

Forms use the same validation rules on both sides. Zod schemas on the frontend mirror the backend's rules, so the user gets instant inline feedback. The backend is still the source of truth, and a 422 from the server maps onto the same form fields rather than becoming a toast. For ordinary expected failures, like trying to sell more units than you have in stock, the backend replies with a 409 carrying a clear sentence, and the frontend shows that sentence to the user verbatim, with the modal still open so they can adjust the quantity. For network errors and unexpected server errors, there's a generic friendly message. The single place where 401 is handled is one Axios interceptor — when the session ends, it clears local caches, toasts a single message, and sends the user back to login. There's no place in the app that has to handle 401 on its own.

When a stock-in or stock-out is recorded successfully, the server's response includes a field called newProductQuantity. The frontend uses that value to update every cached product list immediately, so the row's stock badge refreshes without needing to reload the page. That's the small bit of polish that ties the whole thing together.

## Version C — Full walkthrough (~2100 spoken words)

This project is an Inventory Management System — a small, complete inventory app for tracking products, categories, suppliers, and stock movements. It's split cleanly into two halves that you can build, run, and explain independently: a raw-PHP and MySQL backend that exposes a JSON API, and a React frontend that consumes that API. I'll walk through both halves end-to-end and then take questions.

**The problem the app solves.** Small shops often track stock on paper or in messy spreadsheets, and they end up with the same recurring problems: how much of each product do I actually have, which products are about to run out, when did I last buy from this supplier, and what does my total stock value look like right now. The system I'm building keeps an answer to all four of those questions in one place. The data model is intentionally small — products belong to a category and to a supplier, and every change in stock is a separate immutable record split into a stock-in table and a stock-out table.

**The database.** I have five tables. The products table holds the product's name, its category, its supplier, a purchase price and selling price, a minimum stock level that defines the "low stock" alert, and a quantity that's managed by the server, never by the user. Categories and suppliers are simple lookup tables — a name and a created-at. The stock-in and stock-out tables each store a product reference, a quantity, optional price fields, an optional note, and a created-at. The whole design philosophy is that once a stock record is inserted, it never changes. If you record the wrong quantity, you don't edit it — you record a compensating stock-out to cancel it out, the same way you'd correct a bank ledger. That gives me an honest history I can trust for reports, audits, and debugging. Foreign keys are set up so that deleting a category or supplier simply sets the product's reference to null, and the products table keeps a copy of the supplier's name on each row so historical stock-in records stay readable even after the supplier is gone.

**The backend.** It's raw PHP and MySQL. I deliberately skipped a framework. Every endpoint is a single small PHP file — one for login, one for listing products, one for recording a stock-out — and they share a small set of helpers for database access, response formatting, and session handling. The whole API is JSON, both directions: requests send a JSON body and responses always return JSON with the same envelope — a success boolean, a data field, a human-readable message, and an optional errors object keyed by field name. That uniform shape is what lets the frontend react predictably to every endpoint. Authentication is session-based: when you log in, the server issues an HttpOnly session cookie. The browser attaches it to every subsequent request automatically, the server either accepts it or returns 401, and there's no token to manage anywhere in the JavaScript. The endpoints fall into standard CRUD shapes for the resources that need it — categories, suppliers, products — and dedicated create endpoints for stock-in and stock-out, which compute the new product quantity inside a database transaction so we never end up with a stock record whose math doesn't add up.

**Errors on the backend.** The backend speaks a small, deliberate set of HTTP statuses. 200 and 201 mean success. 422 means the request was understood but didn't pass validation, and the response includes a per-field errors map. 404 means the thing you asked for doesn't exist. 409 is reserved for business-rule conflicts — the only two I have are "this product has stock history, you can't delete it" and "you tried to sell more units than you have in stock." 500 is for anything genuinely unexpected, and for stock-in or stock-out specifically I roll the transaction back so the database is left untouched. The frontend then handles each of those cases differently, and that's where the frontend's contribution shows up.

**Moving to the frontend.** The frontend is a React app built with Vite. It talks to the PHP API over JSON. Three layers are deliberately separated. The lowest layer is an Axios client with the base URL baked in and credentials turned on, so every request carries the session cookie. The middle layer is a set of small files — one per backend resource — that wrap each endpoint in a single function and return whatever the backend sent back. On top of that, TanStack Query hooks own the cache, the loading state, and the error state for each read. And finally the pages and components just render. The rule is that pages never call Axios directly, and the Axios layer never touches the cache. That separation is what lets me swap things in and out without breaking anything else.

**How login works from the user's side.** The very first time you open the app, before any screen renders, there's a single small piece of code that calls an endpoint asking "who am I." If the answer is a user, the app shows the dashboard. If the answer is 401 — which is the normal first-visit case — the app redirects you to the login screen. You sign in with a username and password, the server sets a session cookie, and from then on every request just works. Refresh, close the tab, come back tomorrow — the cookie is still there, and the very first "who am I" call succeeds, so you skip the login page entirely. When you log out, the session is destroyed server-side and the cookie becomes a no-op; the very next protected request will return 401. There is no token in local storage anywhere. There never needs to be.

**State and where each kind lives.** I split state into three buckets. The first is server state — product lists, stock-in history, the dashboard summary. That goes through TanStack Query because it's already on the server, it's already cached there, and trying to mirror it into a global client store would just invite drift. The second is small app-wide state — the current user and the light-or-dark theme — which lives in React contexts at the root of the tree. The third is page-local state — which modal is open, whether you're on page 2, which filter the user picked. And here's a deliberate choice: filters and pagination actually live in the URL's query string, not in component state. That makes views shareable, makes refresh safe, and means the back button does what users expect it to do.

**Forms and validation.** Every form on the frontend is built with the same two libraries: React Hook Form for the wiring and Zod for the rules. Crucially, the Zod schemas mirror the backend's rules field-for-field. The user gets instant inline feedback when they make a mistake — for example, a negative quantity or a missing name — without having to wait on a network round trip. But the backend runs the same checks again, server-side, on every submission, and that's what I treat as the real source of truth. If the two ever drift — say a field I forgot to validate, or a race condition where the rules change between page load and submit — the backend still catches it and returns a 422. The frontend maps that 422 field-by-field back onto the form, so the user sees the same kind of inline error they would have seen had the rule been local. That's deliberate: 422s never become toasts, because field errors belong next to fields.

**Showing errors to the user.** I treat each HTTP status as a separate UI case. 401 — your session ended — is handled in exactly one place: a single Axios interceptor. When it fires, it clears the local caches, toasts one friendly message, and sends the user back to login. No page has its own 401 logic, and there's no retry, because there is no token refresh; the session is simply gone. 422 — bad input — maps onto the form, exactly as I just described. 404 — the thing you asked for doesn't exist — gets a toast with the backend's own message, and the affected list is refreshed in case the row got deleted out from under us. 409 is special: it means the request was understood, the user is authorized, but the action is blocked by a business rule. The two 409s I have are "this product has stock history, you can't delete it" and "you only have four units, you can't sell five." The frontend shows the backend's own message verbatim — those messages were written for end users, so rewriting them would lose information. For 500 and for plain network errors, there is a single generic friendly message and a retry affordance where it makes sense. The Stock In and Stock Out endpoints also get a specific reassuring copy for the 500 case, because the database transaction rolls back and the user genuinely didn't lose anything.

**What happens when you record a stock-out.** Here's one concrete walkthrough. You're on the Products page, you click the sell icon on a row, the modal opens pre-selected to that product. You pick a quantity and a price, and you submit. The frontend posts a JSON body to the stock-out endpoint. The backend opens a database transaction, checks that the product actually exists and that you have enough stock, records the stock-out, updates the product's quantity, and returns a 201 with the new record plus a field called newProductQuantity. The frontend's mutation hook, on success, does two things. First, it proactively patches every cached product list with that new quantity, so the row's stock badge updates immediately without a refetch. Second, it invalidates the queries for stock-out history, the dashboard, and the low-stock report, so the next render picks up any server-side drift. The modal closes, the toast appears, and the user sees the change without any page reload.

**What happens when your session expires mid-use.** You're typing in a modal — say editing a product — and the backend rejects your request with a 401 because the session timed out. The Axios interceptor catches it, clears the auth context, clears every cached query, toasts a single message, and does a hard redirect to the login page. I chose a hard reload over an in-page redirect on purpose: it guarantees a clean state and no lingering background fetches. I haven't built draft recovery, so a mid-edit session loss does mean losing the unsaved input. That's a known tradeoff, not an oversight — and it's the kind of thing I can name out loud and defend if a teacher pushes on it.

**A few answers to likely questions.** The first one is usually "why React Query instead of Redux or Zustand." My answer is that what I'm caching is data that already lives on the server. React Query is built around that exact problem — it manages refetching, staleness, and invalidation for free — whereas a global store would just be me rebuilding the same thing badly with extra steps. The second is "why does the app call that who-am-I endpoint on every reload instead of storing a token." The answer is that the cookie is HttpOnly, which means JavaScript cannot read it. There is no token-shaped piece of data I could store. The server has to be the one to tell me whether I'm logged in, and the cleanest place to ask is right at the top of the app. The third is "what happens if two people record a sale on the same product from two different tabs." The answer is that the backend serializes the transactions — that's what database transactions are for. The first sale wins, the second one gets a 409 because by then the stock is too low, and the user sees that exact message and can adjust. The frontend is honest about it because the backend was honest about it.
